# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

KiloTap is a Flutter/Firebase mobile app: a two-sided recyclable-scrap marketplace connecting Households (sellers, who book scrap pickups) with Collectors (buyers, who accept and haul the scrap) in Davao City, Philippines, plus an Admin role for verification and moderation. It is a BSIT capstone project written up as a G16 ACM paper. **It is a logistics-matching platform, not a pricing app** — there is no in-app pricing, payment, or price-directory feature; the financial transaction happens person-to-person after pickup. Do not add pricing/payment features unless explicitly asked.

`README.md` describes an earlier prototype design (Riverpod, go_router, a `market_prices` collection) that no longer matches the code — see Architecture below for what's actually implemented.

## Commands

```powershell
flutter pub get              # install dependencies
flutter analyze              # static analysis — must be 0 errors/0 warnings before considering work done
flutter run -d <device-id>   # run on a connected/emulated device
flutter clean                # clean build artifacts (use before a build after dependency/Gradle changes)
```

There is no test suite (`test/` is empty) — do not assume `flutter test` covers anything.

Firestore seed data used during development is (re)created with `python3 scripts/recreate_firestore.py`. It wipes and reseeds `UserAccount`, `bookings`, `bookingItems`, `ratings`, `notifications`, `auditLogs`, and `scrapWeights` using a service-account JSON path that only exists on the server (`/root/.hermes/firebase/...`) — treat it as a reference for the schema, not something to run casually.

Firebase config: `firebase.json` targets Firebase project `kilotap-prototype`. `android/app/google-services.json` and `lib/firebase_options.dart` are required to build/run and are gitignored — obtain them locally rather than recreating them from scratch. `firebase.json` also wires up `firestore.rules` (repo root — the real authorization boundary; `role_permissions.dart`/`AuthState` only gate the UI) and the `functions/` Cloud Functions codebase. Deploy each explicitly: `firebase deploy --only firestore:rules` / `firebase deploy --only functions` — functions require the project to be on the Blaze plan.

**Push notifications**: `lib/services/push_notification_service.dart` wraps `firebase_messaging` + `flutter_local_notifications`. On login it stores the device's FCM token in `UserAccount/{uid}.Fcm_Token` (cleared on sign-out). The Flutter app only ever writes to the `notifications` collection (Table 15, `FirestoreService.sendNotification()`) — it never calls FCM directly, since sending a push to another user's device requires a trusted backend. `functions/index.js`'s `sendNotificationPush` triggers on every new `notifications/{id}` doc, looks up the recipient's `Fcm_Token`, and sends the actual FCM push (shows on lock screen via the `kilotap_default_channel` Android channel, declared in both `AndroidManifest.xml` and `push_notification_service.dart`).

## Architecture

**Navigation & auth**: There is no router package — `lib/router.dart` is a hand-rolled `switch` on route-name strings inside `AppRouter.generateRoute`, gating every route through `AuthState.instance.canAccess(route)`. `lib/services/auth_state.dart` is a singleton holding the signed-in user's role (`Household`/`Collector`/`Admin`) and denormalized profile fields (populated on sign-in, cleared on `logout()`). `lib/services/role_permissions.dart` maps each role to a set of permission strings and each route to the permission it requires (`RolePermissions.canAccessRoute` / `hasPermission`); `Admin` bypasses all per-route checks. There's a `VerifiedCollector` role tier in `role_permissions.dart` that grants `acceptPickup` in addition to what plain `Collector` gets, though `AuthState.isCollector`/`isAdmin`/`isHousehold` only distinguish the three top-level roles.

**Data layer**: Everything is Firestore-backed via `StreamBuilder` — there is no local/demo data path. `lib/services/firestore_service.dart` is the single access point: booking streams (`sellerBookings`, `collectorBookings`, `availableBookings`), `bookingItems(bookingId)`, chat (`sendMessage`, `messagesBetween`, `userConversations`), admin queries (`listUsers`, `pendingCollectors`), and name-join helpers. Sell Scrap submits through `createBookingWithItems()` (booking + items in one batch, booking ID generated on the phone via `newBookingId()`); it waits at most 10 s for the server acknowledgement because Firestore persistence (`persistenceEnabled: true`, 100MB cache, in `main.dart`) queues the write offline. The Cloudinary photo upload is the step that needs a connection: on a network failure the request goes to `lib/services/booking_outbox.dart` (Hive box `booking_outbox`, photo copied to app storage via `path_provider`), which retries every 30 s, on app resume, and from the "Waiting to send" card on My Pickups. Never re-send a booking that was already handed to Firestore — a second write by the seller could overwrite an accepted booking back to Pending. `lib/services/sell_draft_store.dart` autosaves the unsent Sell Scrap form (restored on reopen). `lib/services/cache_service.dart` (Hive) backs other offline fallbacks.

**Firestore schema** follows the paper's Tables 7–15 exactly, and field names must not be renamed: `UserAccount/{uid}` (Table 7, common account fields incl. `Role`) → subcollections `ScrapSeller` (Table 8, plus `Address_GPS`, a GeoPoint holding the household's last-used pickup pin — not in the paper's Table 8; set from Sell Scrap's `widgets/pin_location_page.dart`, remembered so returning households don't re-pin, and cleared by `AuthService.updateSellerProfile` when the barangay/city changes; `bookings.PickupGPS` is taken from this pin, not from GPS at submit time) and `ScrapCollector` (Table 9, incl. `Vehicle_Type`, `Vehicle_Capacity_Kg`, live `Current_Latitude`/`Current_Longitude`, `Verification_Docs` — a `{type, url, status}` array populated by the collector via `documents_page.dart`'s camera/gallery capture, Cloudinary-hosted, 5MB cap enforced in `FirestoreService._uploadToCloudinary`, reviewed by Admin in `verify_collector_screen.dart` — and `Address`, not in the paper's documented Table 9 fields but added for parity with `ScrapSeller.Address`, edited via the shared `widgets/address_entry_page.dart` form; likewise `Profile_Photo_URL` (2MB cap), `Birthdate` (Timestamp, 18+), and `Signature_URL` (PNG drawn in `widgets/signature_pad_page.dart`), all Cloudinary-hosted and shown on the Digital ID in `collector_id_card.dart`. The required `Verification_Docs` types live in `lib/core/verification_docs.dart` — the same three for every vehicle type: Valid ID, Vehicle Photo, Barangay Clearance. Per-vehicle approval: `Verified_Vehicles` (admin-only list of approved vehicle types, also not in Table 9) — set to every registered vehicle on full verification; a vehicle added afterward (each `Vehicles` entry may carry a `Photo_URL`) stays pending until approved in the admin Verify screen's Vehicle Approvals queue, can't be made the active `Vehicle_Type`, and `firestore.rules` blocks claiming a booking whose `VehicleRequirement` exceeds the active approved vehicle. Logic in `lib/core/vehicle_verification.dart`; collectors verified before this field existed fall back to their active vehicle as approved); `bookings/{Booking_ID}` (Table 10, plus `PickupType` ('ASAP' | 'Scheduled') and `ScheduledDate` (Timestamp, date and time) — named as in the paper's Figure 12, not listed in Table 10) → subcollection `bookingItems/{Item_ID}` (Table 11); `scrapWeights/{Class_Name}` (Table 12, the weight-lookup reference table); `ratings/{Rating_ID}` (Table 13); `auditLogs/{Log_ID}` (Table 14); `notifications/{Notification_ID}` (Table 15). A `messages/{Message_ID}` collection backs chat but is intentionally *not* one of the numbered paper tables. Likewise `reports/{Report_ID}` (not a paper table): a household or collector reports the other party of a booking from `widgets/report_problem_sheet.dart` (My Pickups, collector navigation screen); fields `Reporter_ID`, `Reporter_Role`, `Target_ID`, `Target_Role`, `Booking_ID`, `Category`, `Description`, `Status` ('Open' | 'Investigating' | 'Resolved' | 'Dismissed'), `Admin_Action` ('None' | 'Warned' | 'Suspended'), `Admin_Note`, `Created_At`, `Updated_At`; reviewed in `screens/admin/reports_screen.dart`.

**Account moderation**: `UserAccount` carries `Account_Status` ('Active' | 'Suspended' | 'Closed'; missing = Active), `Status_Reason`, `Status_Changed_At`, `Status_Changed_By` — not in the paper's Table 7. Only an admin can change them (`firestore.rules` `moderationUnchanged()`), from User Management or a report (`FirestoreService.setAccountStatus`, helpers in `lib/core/account_status.dart`). Nothing is deleted: blocking a household cancels its Pending/Accepted bookings, blocking a collector sets it offline and returns its Accepted bookings to Pending; every change is audited (`SUSPEND_USER` / `CLOSE_ACCOUNT` / `REACTIVATE_USER`) and the user is notified. A blocked account cannot sign in or restore a session (`AuthService._loadUserDataIntoState`), is signed out live if blocked while signed in (`_watchAccountStatus`), is refused by the rules for every shared write (`accountActive()`), and is skipped by dispatch. Permanent deletion is not implemented yet.

**Detection → dispatch pipeline** (models are: `lib/services/ml/*`, `lib/services/scrap_weight_service.dart`, `lib/services/ml/capacity_matcher.dart`, `lib/services/google_maps_service.dart`):
1. A household photo goes through an on-device MOLO model (TFLite) to produce class labels — `lib/services/ml/tflite_runner.dart`, `detection_postprocess.dart`, `molo_architecture.dart`, and `pipeline.dart` are the wiring for this. The bundled `assets/models/molo.tflite` is the MOLO model (MobileNetV2 backbone via Ultralytics' `TorchVision` layer + YOLOv8n neck and head) exported as LiteRT `w8a32` (int8 weights, float32 activations; 4.36 MB, 640x640, float32 channels-first input `(1,3,640,640)`, output `(1,25,8400)` with normalized boxes and 0-1 class scores; `TfliteRunner` letterboxes the photo like training does — EXIF-upright, aspect kept, centred, grey 114 padding — and maps boxes back to photo-relative coordinates): 21 scanner **sub-classes** (battery, cardboard, copper, crt_television, flatscreentv, hair_dryer, keyboard, laptop_computer, microwave, mobile_phone, motorcycle_block, mouse, plastic_hdpe, plastic_pet, refrigerator_standard, splittype_aircon, vehicle_part_big, glass_bottle, metal_can, paper, washing_machine), in the exact order of `DetectionPostprocess.classNames`. `plastic_bottle` was merged into `plastic_pet` for this model; `ScrapWeightService.legacyPickerClass` still redirects it for old data. `vehicle_part_big` is in the model but listed in `DetectionPostprocess.hiddenClasses` (never reported; AP 0.03 on test). The confidence threshold is 0.30 (the paper's 2.3.2.1.2 says 0.50 — the paper needs updating). Results (dataset v3, 15,777 train / 679 val / 354 test images, 17 of 21 classes have test data; glass_bottle, metal_can, paper and washing_machine have none): validation mAP@0.5 83.2% (MOLO) vs 83.1% (YOLOv8n baseline, same data and settings; YOLOv8n is smaller, 3.1M vs 3.8M params); held-out test mAP@0.5 82.8% / mAP@0.5:0.95 65.5% (PyTorch), **79.7% / 59.9% for the bundled w8a32 file**. Phone inference time is logged as `KiloTapML inference ...ms` (not yet measured). The sub-classes are what a scan outputs and what the Sell Scrap item picker lists; the 6 collector-preference **categories** (`MaterialPreferences.categoryMap`) group them for Find Scrap matching. The LiteRT exporter also writes most weight buffers as external offsets at the end of the file; the app's runtime cannot resolve those (logcat: `E/tflite: Input tensor N lacks data`, surfaced as "Bad state: failed precondition"), so every new export must be repacked with all buffers inline (`training/repack_inline.py`, outside the repo) before bundling. Do not bundle a full-int8 (`quantize=8`) export: its float-input-to-int8 graph has no QUANTIZE ops and the app's runtime (`tflite_flutter` 0.12.1, LiteRT 1.4.0) rejects it with "Bad state: failed precondition". Training pipeline lives outside the repo (Colab notebook `KiloTap_train_eval_v3.ipynb`, `prepare_dataset.py`, `merge_extra_dataset.py`, `taxonomy.py`).
2. `ScrapWeightService` does a static class-name → weight/size-class lookup (the in-app `_cache` is authoritative; the `scrapWeights` collection mirrors it as a reference table). Weights for the newer sub-classes are estimates.
3. `CapacityMatcher.match()` (`lib/services/ml/capacity_matcher.dart`) turns total kg into a `VehicleSize` by fixed thresholds — `<20kg` Pushcart, `<100kg` Tricycle Sidecar, `<500kg` Multicab, else Truck — then bumps the result up one tier if any item's size class is `"Heavy Override"` (capped at Truck), regardless of total weight. This is the "recommend, don't enforce" rule: the collector still makes the final call.
4. `GoogleMapsService.getRoute()` (`lib/services/google_maps_service.dart`) calls the Distance Matrix API for driving distance/ETA between two coordinates, with an Hive-backed LRU cache (`route_cache` box, 20 entries) as an offline/no-key fallback — it explicitly checks for the literal placeholder value `AppConstants.googleMapsApiKey == 'YOUR_GOOGLE_MAPS_API_KEY'` and skips the network call in that case. `lib/services/routing_service.dart` sits above this for higher-level routing/ranking use. `lib/core/constants/app_constants.dart` holds the key — it is tracked in git with the placeholder value; a real key is only ever added there as an uncommitted local edit and must never be pushed.

**Dispatch and audit (Cloud Functions, `functions/index.js`)**: `fanOutNewBookingNotifications` alerts only the nearest 5 eligible collectors (Verified, online, vehicle tier and material preferences match; ranked by straight-line distance from `Current_Latitude`/`Current_Longitude` to `PickupGPS`, collectors without a location last). `widenPendingBookingAlerts` (scheduled every minute, needs Blaze) reminds each alerted collector once after 5 minutes and alerts the next 5 nearest every 10 minutes while the booking is still Pending, for up to 60 minutes; who was alerted is derived from existing `notifications` docs. Every eligible collector can still see the booking in Find Scrap. `auditBookingStatusChanges` writes an `auditLogs` entry (`BOOKING_ACCEPTED`/`BOOKING_COMPLETED`/`BOOKING_CANCELLED`, `Ip_Adress: "server"`) when a booking changes status — server-side because auditLogs is admin-only in the rules. On the collector side, "I've Arrived" only notifies the household (Type `on_the_way`); "Complete Pickup" is a separate confirmed step, and `screens/collector/booking_pass_screen.dart` is the live Booking Pass (digital transaction pass, paper 2.1.3.1.12) shown at subdivision gates.

**Screens** are organized by role under `lib/screens/{account,household,collector,admin}/`, one screen per file, wired into `router.dart` by route-name string. `lib/core/theme/app_colors.dart` and `lib/core/constants/app_constants.dart` hold the shared color tokens (flat palette, no gradients — Seller Green `#1B8A5A`, Buyer Blue `#1A85C8`) and shared enums (`vehicleTypes`, booking/verification status strings, Firestore collection name constants). The collector-facing UI shows weight in kilos only, never currency — pricing/payment is out of scope.

## Conventions

- No emojis anywhere (code, comments, UI text, commit messages). No gradients — flat colors only.
- `flutter analyze` clean (0 issues) before calling work done.
- Prefer block-body `{ return ...; }` over arrow-body (`=>`) for any widget tree longer than ~2 lines.
- Wrap `ListTile` in `Material`, never `Container` + `BoxDecoration` (breaks ink splash / asserts on Flutter Web).
- One screen = one `.dart` file. No duplicate logic — extract shared helpers.
- Files under `lib/screens/household/` and `lib/screens/collector/` import shared code via `../../core/`, `../../services/`, `../../models/`.
- Vehicle types are exactly `Pushcart`, `Tricycle`, `Multicab`, `Truck` (no parenthetical descriptions in UI); size classes are `S`/`M`/`L`/`Heavy Override` (no raw kg as the primary display).
- Flutter 3.44 renames — don't reintroduce the old names: `withOpacity` → `withValues(alpha:)`, `activeColor` (Switch/Radio) → `activeThumbColor`, `CardTheme` → `CardThemeData`. `borderLeft` isn't a valid `BoxDecoration` param — use `border: Border(left: ...)`.
- Don't combine Firestore `array-contains` with `orderBy` on a different field (forces a composite index) — sort in Dart instead.
- On Flutter Web, edge-to-edge headers break `SafeArea`/`AppBar`/`PreferredSize`; use `Column` + `Container(padding: EdgeInsets.only(top: MediaQuery.padding.top + 16))` + `Expanded(ListView)` instead, wrapping only the bottom nav in `SafeArea`.
- Removing a class field needs a hot restart (`R`) — hot reload (`r`) won't pick it up.

## Workflow

**Before making any code or design change, no matter how small, run this checklist and get explicit go-ahead — do not edit files first and explain after:**
1. State what the change is and why, in a sentence or two.
2. Check it against this file's "What this is" section — confirm it doesn't drift into pricing/payment/rate-directory territory or otherwise stray from the logistics-matching purpose.
3. Check it against the relevant doc source: this file's Architecture/Schema section for anything touching data models, routing, or the detection pipeline; the G16 ACM paper (Tables 7-15, the requirements in §2.1.3, the vehicle-capacity thresholds in §2.3.2.2) for anything that should match the paper's spec.
4. Present a short plan (what files, what changes) and wait for the user's explicit approval before editing.
5. Do not push to git without separate explicit approval, even after an edit was approved — treat push as its own gated action, not implied by an approved edit.

This supersedes any earlier "just make the change" default — always plan, verify, and ask first here, for every change.

- Never edit `.dart` files with a code-execution/eval tool — it has corrupted source before (merged imports into widget code, broken string literals). Use a full-file rewrite or a targeted diff-style edit instead. After 3+ failed patch attempts on one file, stop patching and rewrite it clean.
- Before pushing, verify bracket balance (`(`/`)`, `{`/`}`) on every changed file, and never push code known to be broken.
- Prefer the simpler fix — removing a problematic feature over adding complexity to accommodate it.
- Never commit `google-services.json` or `firebase_options.dart` (Firebase credentials, gitignored). Never push a real Google Maps API key — `lib/core/constants/app_constants.dart` must keep the `YOUR_GOOGLE_MAPS_API_KEY` placeholder in the repo; a real key is a local-only, uncommitted edit.
